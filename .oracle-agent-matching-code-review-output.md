## 1. Verdict

**Reject** — the shipped revision still has consequential Pi integration failures, an ACK-without-persistence path, permanently excluded changed-input `no_match` rows, and incomplete ID-safety checks.

## 2. Five consequential remaining issues

I extracted and inspected all 28 files, including both Markdown documents. Source locations below refer to the attached files. Dependency behavior was checked against **Pi v0.85.1, the version baseline specified in the plan**; the archive does not contain the deployment lockfile.

### 1. The real Pi adapter is incorrectly initialized; the queue test bypasses it

**Location:** [`libs/agent-match/runner.ts:24–37`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/agent-match/runner.ts).

```ts
const models = createModels();
const model = models.getModel("openrouter", modelId)
  ?? models.getModel("openai", modelId);
```

In Pi v0.85.1, `createModels()` creates an **empty provider collection**. This function never registers either provider, so both lookups return `undefined` and execution throws `Unknown agent match model` before starting the agent. Merely installing the packages does not register providers in this instance. 

There is a second adapter error immediately afterward: `streamFn: models.streamSimple` passes an **unbound instance method**. Once provider registration is fixed, this still loses the `Models` receiver. Pi’s own integration example explicitly registers a provider and uses `models.streamSimple.bind(models)`. 

The supplied queue success test replaces `agentMatchRuntime.runPiSession` wholesale (`test/agent-match-queue.test.ts:99–111`), so it cannot detect either defect.

**Smallest correction:** register only the configured provider, bind or wrap `streamSimple`, and add an adapter smoke test that does not replace `runPiSession`. These failures currently mask the downstream agent defects below; they do not make those defects safe.

### 2. Pi-caught failures can become semantic `no_match` or an ACK without a persisted outcome

**Locations:** [`runner.ts:60–73, 105–147, 158–180`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/agent-match/runner.ts), [`queue.ts:11–16`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/agent-match/queue.ts), `tools.ts:172–177`.

The outer queue handler correctly retries **outwardly thrown** errors. The remaining problem is that the runner does not reliably throw operational failures outward.

Pi catches tool exceptions and turns them into error tool results. Its agent lifecycle also records run failures rather than necessarily rejecting `prompt()`. The adapter checks neither tool-error events nor the final error state. 

A concrete ACK failure path is:

```text
conclude_match starts
→ concluded = true
→ applyAgentVerdict throws before committing D1
→ Pi catches the tool exception
→ the model finishes without a successful second conclusion
→ runner skips its fallback because concluded is already true
→ runner returns the default lastStatus = "no_match"
→ queue calls ack()
```

**No verdict was persisted.** Recovery may eventually reclaim the still-running row, but the original delivery was incorrectly acknowledged and the next attempt can pay for the model again.

Separately, a provider failure before any conclusion can resolve the session and reach the `agent_no_conclusion` writer, converting infrastructure failure into a semantic miss. `lift_imdb_series` makes this even easier by returning `{error: "imdb_lookup_failed"}` as an ordinary successful tool result.

**Smallest correction:** track operational failure and durable completion separately, outside the model transcript. Set completion only after the writer returns; propagate an unresolved operational failure to the consumer instead of executing the semantic fallback. **Changing the tool to `throw` alone is insufficient**, because Pi catches tool exceptions.

### 3. The pool permanently excludes evaluated misses—even when their real inputs change

**Locations:** [`pool.ts:14–20, 54–75`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/agent-match/pool.ts), [`writer.ts:95–107`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/agent-match/writer.ts).

The eligibility predicate is:

```sql
agent_state = 'no_match'
AND next_agent_at <= :now
AND agent_input_hash IS NULL
```

Every claim supplies a non-null hash, and the `no_match` writer preserves it. Therefore an evaluated miss never reaches any current-input comparison.

The hash supplied on first claim is also based on:

```ts
{ doubanId, title: String(doubanId), type: "unknown", imdbId }
```

Subsequent claims reuse the existing hash rather than recomputing it. A corrected Douban title/year/type or a new policy version cannot reactivate the row through the intended comparison.

**Important qualification:** the locked spec explicitly says **unchanged inputs stay skipped even after backoff expires**. The defect is not “every expired miss must run again”; it is that **changed inputs cannot become eligible**.

**Smallest correction:** hash the actual Douban input and current policy, compare that with the previous evaluated hash, and retain the backoff and suggested-state exclusions. Simply deleting the hash condition would introduce unnecessary repeat spending.

### 4. Auto-write checks retrieved membership, but not sufficient title evidence or human rejection

**Locations:** [`verifier.ts:49–100`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/agent-match/verifier.ts), [`tools.ts:95–159`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/agent-match/tools.ts), `writer.ts:19–34`.

The verifier receives Douban `title` and `originalTitle` but never examines them. I exercised the actual verifier with the existing **Inception / 2010** source fixture and a **synthetic registered movie candidate with an unrelated title, the same year, no IMDb, and confidence `0.95`**. It returned:

```text
tier: "auto"
code: "auto"
```

This is not a claim about a particular real TMDB record. It demonstrates the concrete boundary failure: `search_tmdb` lets the model choose the query, and any returned same-type candidate without a large movie-year conflict can pass. Closed-set membership proves retrieval, not identity.

Two related safety omissions remain:

* **IMDb comparison is optional in practice.** The model can omit `get_tmdb_external_ids`; the verifier then sees an absent candidate IMDb instead of a potentially discoverable conflict. The selected candidate should be hydrated by code before applying the conflict rule. A successful lookup returning no IMDb must still allow auto-write.
* **Rejected candidates are neither excluded nor preserved across verdicts.** Reject records the ID, but runner/verifier never consult it, and `buildAgentResult()` drops the rejection list. A shipped re-entry path already exists: reject → ordinary uncalibrated save clears `agentState` → claim → same candidate can be selected again.

**Smallest correction:** add the title check described in section 4, enforce selected-candidate enrichment independently of model tool choice, and apply/preserve the per-row rejected-candidate set.

### 5. Two other write paths can splice together IDs belonging to different works

**Locations:** [`routes/dash/tidy-up/detail.tsx:56–73`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/routes/dash/tidy-up/detail.tsx), [`libs/api/index.ts:62–67`](sandbox:/mnt/data/agent-match-review-3p4f8ym1/apps/core/src/libs/api/index.ts).

The dedicated agent writer correctly writes the candidate tuple as a unit. These paths do not.

**Confirming an IMDb-conflict suggestion:**

```text
existing:   TMDB=null, IMDb=tt1111111, Trakt=11
suggestion: TMDB=202,  IMDb=tt2222222, Trakt=22

confirmed:  TMDB=202,  IMDb=tt1111111, Trakt=11
            calibrated=true, matchSource=human
```

The three independent `existing ?? suggested` expressions create a mixed tuple and then human-lock it. This directly affects the locked policy’s intended IMDb-conflict → suggestion workflow.

**A stale generic persist:**

```text
existing: TMDB=101, IMDb=tt101, Trakt=1
incoming: TMDB=202, IMDb=tt202, Trakt=2

stored:   TMDB=101, IMDb=tt202, Trakt=2
```

The existing-TMDB `CASE` guard is present and works; the unconditional IMDb/Trakt `COALESCE` assignments undermine tuple integrity. `test/persist-id-mapping.test.ts:8–15` actually expects the incoming IMDb to survive beside the preserved TMDB.

**Smallest correction:** when confirming a pending suggestion, adopt its tuple atomically, including nulls. When generic persistence rejects a conflicting incoming TMDB, also reject the companion IDs from that conflicting tuple. Keep ordinary empty-value preservation for compatible updates.

## 4. Tightest remaining auto-write risk and the smallest additive verifier rule

**The immediate residual poisoning risk is a retrieved, same-type, same-year wrong title receiving high model confidence.** The shipped verifier demonstrably accepts it. No Douban↔IMDb identity-chain requirement is needed to close that path.

The smallest useful addition is an **auto-write-only title-compatibility check**:

> Before auto-writing, require a supported match between a normalized Douban title/original title and a tool-derived candidate title/original title or verified alias; otherwise downgrade an otherwise valid candidate to `suggest`.

Use conservative normalization—Unicode, case, punctuation and whitespace. Preserve meaningful sequel numbers. Handle explicit season suffixes only where the comparison intentionally targets a parent show. Do not let the model invent aliases to satisfy the verifier.

This retains the locked decisions:

* **No Douban IMDb is required.**
* **Missing year alone does not veto auto-write.**
* A known IMDb conflict still downgrades to suggestion.
* A clear movie-remake year conflict still prevents auto-write.
* Closed-set and type checks remain mandatory.

Code-owned candidate enrichment and rejected-ID exclusion enforce existing safety decisions; they are not substitutes for an IMDb-chain gate.

The title check closes the reproduced wrong-title path, but it cannot prove identity for genuinely same-name, same-year works. That residual ambiguity is real; confidence alone does not eliminate it. It is not a reason to reinstate the rejected IMDb-anchor policy.

## 5. Smallest post-implementation delta

Keep the deterministic matcher’s lookup order and unique-hit rules, the six-tool interface, the model-free request paths, the hourly cap, and the dedicated conditional writer.

Patch the existing boundaries: **Pi initialization and error propagation; actual-input hash comparison; lease validation; title/enrichment/rejection verification; and tuple-atomic confirm/upsert behavior.** Cron needs only enough per-row input/outcome information to distinguish genuine leftovers from operational failures—not a new matching strategy.

The focused regression coverage should exercise the real Pi adapter with fake streams, failed D1 conclusion followed by session completion, provider/tool errors versus genuine no-conclusion, changed versus unchanged expired hashes, rejected-candidate re-entry after save, expired-token acquisition, wrong-title auto-write rejection, and conflicting-tuple confirmation/persistence. Retain positive tests proving that **no IMDb and missing year can still auto-write**.

**Verification performed:** the six supplied verifier tests passed after isolated TypeScript transpilation. Additional probes against the actual verifier reproduced the unrelated-title `auto` result and the medium-confidence year-conflict `none` result. I also checked the problematic tuple expressions and SQL predicates independently. The selected bundle lacks the full D1/Worker test harness and dependency lockfile, so this is **not** a claim that the full integration suite was executed or passed.
