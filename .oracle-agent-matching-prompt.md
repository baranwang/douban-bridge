You are reviewing a design for adding an LLM agent into an existing Douban→TMDB/IMDb/Trakt ID-mapping pipeline.

## Product
This is a Cloudflare Workers addon (`stremio-addon-douban`). Core Worker stores Douban ID mappings in D1 (`douban_mapping`) with `doubanId`, `tmdbId`, `imdbId`, `traktId`, `calibrated`. Stremio catalog/meta quality depends on correct TMDB/IMDb IDs (posters, logos, cross-addon linking). A wrong match is worse than no match.

## Current matching

Two deterministic paths already exist. Do not assume they are the same.

### 1. Request path: `api.findExternalId()` in `apps/core/src/libs/api/index.ts`
Used by catalog/meta enrichment when a Douban ID is missing from D1.
1. Scrape Douban subject desc for IMDb ID.
2. If IMDb exists, Trakt `/search/imdb/{id}` and accept only if exactly 1 result.
3. Else search Trakt by title (`movie`/`show`), accept exactly 1 result, else exact title/original_title match after stripping “第X季”.
4. Persist via `persistIdMapping`. `calibrated=true` rows are never overwritten.

This path does NOT:
- lift season IMDb IDs to parent series
- compare years
- search TMDB
- mark `calibrated`

### 2. Hourly cron: `apps/core/src/cron.ts` (`0 * * * *`)
Selects rows where `tmdb_id IS NULL` AND `calibrated` is not true. Batches of 10.
1. If stored `imdbId`: Trakt search by IMDb. If 0 hits and Douban type is TV, query unofficial IMDb API for parent series ID, then Trakt-search that. Accept only exactly 1 Trakt result.
2. Else/fallback: Douban subject detail, Trakt search by Chinese title. Accept if exactly 1 result, else unique `original_title` match, else for movies unique year match.
3. On success: persist IDs and set `calibrated: true`.
4. Failures are skipped; item remains eligible next hour. Single-item failures do not abort the batch.

### 3. Human path
`/dash/tidy-up` lists rows missing TMDB ID. Detail page re-searches TMDB/Trakt and lets a human write IDs + `calibrated`.

## Constraints already agreed with the user
- Keep deterministic unique-hit matching as the first stage.
- Agent only handles leftovers the deterministic logic cannot 100% match.
- Do not run the model on catalog/meta request hot path.
- Model cannot invent IDs; it may only pick from closed candidate sets or tool results that then go through a code verifier.
- Agent must never set `calibrated=true` (that flag is a human lock).
- High-confidence + verifier-pass results SHOULD auto-write official IDs (`matchSource=agent`, `calibrated=false`).
- Medium confidence → suggestions only for tidy-up.
- Low / verifier fail → `no_match` with backoff.
- Do not bolt LLM calls onto the existing hourly cron (timeout/cost). Prefer enqueue + separate consumer.
- Phase 1: Ranker + Verifier + suggest/auto-write. Investigator (tool-using re-search) is phase 2.

## Proposed design to judge
Pipeline:
1. Deterministic matcher runs as today. Unique hit writes official IDs. Ambiguous/empty/season-id-failure records `unmatchedReason` + candidate snapshot and status `pending_agent`.
2. Ranker (cheap JSON model): input = Douban detail + existing Trakt/TMDB/IMDb candidates. Output = `pick(candidateId)` or `none` + confidence + short reason. Cannot mint IDs.
3. Investigator (phase 2): only if candidates empty, contradictory, remake, or season/title-translation issues. New search hits become candidates, never direct writes.
4. Code verifier required for auto-write:
   - type match (movie↔movie, tv↔show; episode/season must lift to parent show)
   - year delta ≤ 1; missing year on either side blocks auto-write
   - title match: exact original_title OR cleaned Chinese title vs title/original_title
   - if both sides have IMDb, they must be identical
   - pick must be from closed candidate set
5. Storage additions on `douban_mapping` (or equivalent):
   - matchSource: deterministic | agent | human
   - matchStatus: unmatched | pending_agent | suggested | matched | no_match
   - suggestedTmdbId/ImdbId/TraktId
   - unmatchedReason, agentConfidence, agentReason, agentAttempts, nextAgentAt
6. Runtime: hourly cron stays deterministic + enqueue. New Queue consumer processes a few Ranker jobs at a time. Candidate snapshots live in queue payload, not giant D1 JSON.
7. tidy-up becomes: pending suggestions / auto-written-unreviewed / no_match, not just “missing TMDB”.

## Your job
Act as a skeptical staff engineer. Judge this design against the actual code.

Please return:
1. Verdict: approve / approve-with-changes / reject. One sentence why.
2. The 3-5 most important design changes, if any. Be concrete (schema, verifier rules, queue vs cron, write policy).
3. Hidden footguns in the *current* code that this design must not inherit (especially cron vs request-path mismatch, calibrated semantics, unique-hit false positives/negatives).
4. Whether phase-1 Ranker-only is actually enough for the real unmatched set, or the current unmatched cases are mostly empty-candidate / season-IMDb / remake problems that need Investigator immediately.
5. A tighter auto-write policy than “high confidence + verifier pass”, if you think the current verifier is still too loose or too strict for this catalog.
6. Minimal schema/runtime you would actually ship in v1. Cut anything ceremonial.

Do not propose rewriting the deterministic matcher unless a specific bug forces it. Prefer the smallest design that will not poison TMDB IDs.
